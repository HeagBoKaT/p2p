# Правила для Claude Code в этом репозитории

## Проверка сборки — только в Docker

Любая проверка компиляции (`dotnet build`, `dotnet publish`) выполняется внутри Docker,
через [Dockerfile](Dockerfile) в корне репозитория, а не напрямую на хосте:

```bash
docker build -t p2p-build .
```

**Почему.** Прошлый раунд проверок гонял `dotnet build`/`publish` и автоматизированные
UI-тесты прямо на хосте пользователя. Это дважды аукнулось: тестовый запуск случайно
подхватил реальный профиль (`%APPDATA%\p2p`) вместо изолированного, и несколько
экземпляров `p2p.exe` из разных прогонов зависли в чужих сессиях, которые не получилось
надёжно прибить (`taskkill`/`Stop-Process` не имели прав через границу сессии). Сборка в
контейнере с этим классом проблем не сталкивается в принципе — исключено само наличие
хостовых файлов/процессов/сессий, которые можно случайно задеть.

**Что можно проверить в контейнере.** WPF-проект (`net10.0-windows`) собирается и в
Linux-контейнере — таргетинг-пакет `Microsoft.WindowsDesktop.App` тянется через NuGet
для компиляции без исполнения. Это покрывает `dotnet build`/`dotnet publish` и любые
Roslyn-анализаторы/warnings-as-errors — то есть основную массу правок.

**Что в контейнере не проверить.** Реальный GUI-прогон, клики, скриншоты — контейнер без
desktop-сессии этого не может (см. [UpdateService.cs](Services/UpdateService.cs) — там
понадобилась именно интерактивная UI-автоматизация на хосте, чтобы найти баг с кодовой
страницей cmd.exe). Для такого явного интерактивного теста на хосте — явно спросить
пользователя и обязательно поднимать процесс с изолированными `--data-dir`/`--port`,
никогда не подключаясь к реальному профилю (`AppData\p2p`) или боевому порту.
